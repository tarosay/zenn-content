子供たちとmicro:bitを使う作品のため、受信側micro:bitを2台PCへUSBシリアル接続する構成を考え、Web Serial APIを使うScratch拡張機能を作りました。最初は「`requestPort()`を2回呼べばよい」と考えていましたが、実機では**2台目の選択ダイアログが出ません**。

この問題はmicro:bit固有ではなく、**Web Serial APIで複数のポートを開くときの問題**です。作った拡張も機器をmicro:bitに限定せず、PCが認識するシリアルポートを個別に管理する設計です。拡張機能には、行単位の文字列を読むブロックと、0〜255を1バイトずつ読むブロックがあります。**ポート選択は受信データの形式とは独立した処理**です。

さらに、失敗時のエラーを捕まえてやり直す方法を試すと、予想した`SecurityError`ではなく`NotFoundError`になったり、1台目と同じポートが返ってきたりしました。

最終的には、**2台目以降は自動的に次のクリックを待つ**設計に変更しました。

この記事は、Xcratch用拡張機能「[マルチシリアル接続](https://github.com/tarosay/xcratch-multi-serial)」の開発記録です。**2026年10月13〜14日のポート接続の実機検証を中心に、観測した事実と原因が未解明の部分を分けて**書きます。

関連記事（紹介編・使い方）：[micro:bitから始まった、複数のUSBシリアル機器を扱えるScratch拡張](https://zenn.dev/tarosay/articles/xcratch-multi-serial)

## 前提：`requestPort()`は好きなタイミングで呼べない

Web Serial APIで未選択の機器を選んでもらうには、ブラウザの`navigator.serial.requestPort()`を呼びます。

この呼び出しには**transient user activation（利用者の操作による一時的な有効化）**が必要です。つまり、利用者がクリックするなどした直後でなければ、ポート選択の画面を開けません。

また、通常のWeb Serial APIでページが得るポート情報からは、Windowsの`COM5`のような名前や、機器固有のシリアル番号を確実に取得できません。`SerialPort.getInfo()`で得られるのはUSBのVendor ID・Product IDなどです。

そのため、この拡張機能では、利用者が選択したポートを内部的に「シリアル通信1」「シリアル通信2」……という番号に割り当てています。WindowsのCOM番号とは無関係です。

`requestPort()`には機器を絞り込む`filters`も指定していません。例えばArduinoとESP32など、**種類の異なるシリアル機器も別々の通信番号で扱えるようにする**ためです。ただし、実機で同時受信を確認したのはmicro:bit 2台で、他機器との組み合わせは未検証です。

- [MDN: Serial.requestPort()](https://developer.mozilla.org/en-US/docs/Web/API/Serial/requestPort)
- [MDN: SerialPort.getInfo()](https://developer.mozilla.org/en-US/docs/Web/API/SerialPort/getInfo)

## 最初の思い込み：緑の旗からは開けない？

実装前の仕様書には「Scratchの緑の旗からポート選択ダイアログは出せない」と書いていました。参考にしたWebHID拡張のコメントからの推測で、**まだ実機確認はしていませんでした**。

ところが2026年10月13日、v0.1.0を作って試すと、**緑の旗からでもダイアログが出ました**。旗を押す操作も利用者によるクリックだからです。

そこで、次のようにブロックを並べました。

```text
緑の旗が押されたとき
  シリアル通信 (1) を ボーレート (115200) で開始する
  シリアル通信 (2) を ボーレート (115200) で開始する
```

期待したのは、1台目の選択に続いて2台目も選べること。しかし、**実際には2つ目の選択ダイアログが出ませんでした**。

「1クリックで1つしか出せなかった」のは、今回の環境での**実機観測**です。Web Serial APIが、いかなる状況でも「1クリックにつき1回」と規定している、と言い切るものではありません。1台目で一時的な有効化を消費したのか、選んでいる間に失効したのかも区別できていません。

## 第1案：`SecurityError`になったら次のクリックを待つ

最初に考えたのは単純な方法です。

1. 2つ目の`requestPort()`も呼んでみる。
2. 操作の権利がなければ`SecurityError`になるはず。
3. そのエラーを捕まえ、次のクリックまで待つ。

ChromeのBlink側の実装（`serial.cc`）も調べ、transient activationがなければ`SecurityError`になる処理を確認していました。

しかし、実機で見た現象は違いました。

| 1台目のダイアログでの操作 | 2つ目の要求で起きたこと |
|---|---|
| すぐポートを選んだ | `NotFoundError`（キャンセルと同じ扱い）になり、「選ばれませんでした」と表示された |
| 10秒ほど待ってから選んだ | 1台目と**同じポート**が返り、「ほかの番号で使っています」と表示された |
| 「〇秒待つ」の後で開始した | クリック直後でないため失敗した |

`NotFoundError`を一律に再試行扱いにすると、本当に利用者がキャンセルした場合との区別がつきません。そもそも「同じポートが返る」現象は、`SecurityError`を待つ作りでは防げません。

**10秒待つと同じポートが返った理由は、現在も分かっていません。** 事実として再現したことと、原因を説明できることは別です。

そこで方針を変えました。**2つ目のダイアログを続けて出そうとしない**ことにしたのです。

## 3案を比較して、次のクリックを待つ方法を採用

| 案 | 検討結果 |
|---|---|
| 1台ずつ「開始する」ブロックをクリックしてもらう | 複数台接続のための拡張なのに操作が煩雑 |
| 許可済みポートを自動列挙して空き番号に割り当てる | どのmicro:bitが何番になるか保証できない |
| **2台目以降はクリック待ちにし、次のクリックで選択ダイアログを出す** | **採用** |

利用者から見た操作は、次のようになりました。

```text
緑の旗をクリック
  ↓
1台目を選ぶ
  ↓
「画面をクリックしてください」
  ↓
画面をもう一度クリック
  ↓
2台目を選ぶ
```

これなら、開始処理を旗の下にまとめて書けて、利用者は次のクリックを行うだけです。

### クリックを覚えておく

現在の実装では、クリックがあったかどうかを`_clickUnused`で管理しています。クリックした直後に使える権利を、**どの「開始する」に割り当てたかを管理するためのアプリ側のフラグ**です。ブラウザ内部のtransient activationそのものではありません。

実際のソースの該当部分は次のとおりです。

```javascript
window.addEventListener('click', () => {
    this._clickUnused = true;
    setTimeout(() => this._serveClickWaiter(), 0);
}, true);
```

第3引数の`true`は、イベントを**capture段階**で拾うためです。画面の部品がイベント伝播を止めても取りこぼしにくくなります。

`setTimeout(0)`を挟むのは、押されたのがScratchの**止めるボタン**だった場合、先にプロジェクト停止処理で接続待ちを取り消すためです。`setTimeout(0)`であっても常にactivationが維持されると一般化はできませんが、この環境ではポート選択が動くことを実機確認しました。

### 2つ目以降は、初めから待機キューへ

ポートを選ぶ処理は、クリックをまだ使っていないか確認します。以下は[実装コード](https://github.com/tarosay/xcratch-multi-serial/blob/main/scratch-vm/src/extensions/scratch3_multiserial/index.js)から、説明に不要なログ処理を省いた抜粋です。

```javascript
_choosePort (index, baudRate) {
    // 同じクリックで2つ目を開こうとしない
    if (!this._clickUnused) return this._waitForClick(index, baudRate);
    this._clickUnused = false;
    this.states[index] = 'choosing';
    return navigator.serial.requestPort().then(
        port => this._assign(index, port, baudRate),
        error => {
            if (error && error.name === 'NotFoundError') {
                this.states[index] = 'cancelled';
                return;
            }
            if (error && error.name === 'SecurityError') {
                return this._waitForClick(index, baudRate);
            }
            this.states[index] = 'openFailed';
        }
    );
}
```

`_waitForClick()`は、開始要求を待機配列に入れます。次のクリックで`_serveClickWaiter()`が**先頭の1件だけ**を取り出し、ダイアログを開きます。待っている要求が複数あれば、1クリックにつき1件ずつ、待ち始めた順に処理します。

止めるボタンでは`PROJECT_STOP_ALL`を受けて待機をキャンセルします。「終了する」ブロックでも対象の待機を取り消せます。

重要なのは、**失敗を検出してから待つのではなく、最初から余計な`requestPort()`を呼ばない**設計に変更したことです。

この変更は、v0.1.0から約1時間後のコミット[`53354c0`](https://github.com/tarosay/xcratch-multi-serial/commit/53354c0)で加えました。

## 追加の問題：受信イベントの中に「開始する」を置くと？

テスト中、行受信イベントの「受け取ったとき」（現在の表記は「1行受け取ったとき」）や「ずっと」の中に「開始する」を入れると、**クリックのたびに選択ダイアログが出る**ことにも気づきました。

対策として、すでに受信中の番号で「開始する」が実行されても**何もしない**ことにしました。ボーレートを変更したいときは、先に「終了する」を実行します。

また、Scratch拡張の接続状態ボタン（「！」）から接続する方法もありますが、この拡張では採用しませんでした。接続対象が最大8個あるのにステータスボタンが1つでは状態を誤解しやすいため、**開始方法はブロックに統一**しています。

## Electronでも同じ問題に遭遇

2026年10月14日、Windowsデスクトップ版のために**Electron 15.3.1**で実験しました。ここでもクリック直後でなければ`requestPort()`は`SecurityError`になり、「次のクリックを待つ」仕組みが必要でした。

しかも、Electronは通常のブラウザと違い、**ポート選択ダイアログを自動で用意してくれません**。そこでアプリのmainプロセス側に、候補のポート名を並べて選択するダイアログを実装しました。

先に作った小さな試験アプリでは、次の点も確かめています。

- `data:` URLで開いた画面ではWeb Serialを使えなかったが、`file://`では使えた。
- 選択操作を遅らせても`requestPort()`は結果を待ち続けた。
- 1回の操作で`requestPort()`を2つ続けて呼ぶと、先の要求が`NotFoundError`になり、後の要求だけがダイアログを出した。

デスクトップ版では、ブラウザ版と**同じ拡張コード**を使っています。ポートの選択画面だけがElectron側の実装です。

なお、公式Scratch Desktopと名前が衝突しないよう、アプリ名・appId・インストーラ名も変更しました。こちらはブラウザAPIとは別の、デスクトップアプリとしての配慮です。

## この件で分かったこと、まだ分からないこと

### 実際に確かめたこと

- 緑の旗から1台目の`requestPort()`は呼べた。
- 旗の下に2つ開始を並べると、2つ目の選択で問題が起きた。
- 2つ目を初めからクリック待ちにする方法で、2台を接続できた。
- Windowsデスクトップ版（Electron）でも同じクリック待ち方式を利用できた。
- Xcratch版とデスクトップ版で、micro:bit 2台からの受信を確認した。

### 未解明・未検証のこと

- 2つ目のダイアログを出せない理由が、activationの消費か時間切れかは切り分けられていない。
- 1台目の選択を10秒ほど待つと、2つ目に同じポートが返った理由は分かっていない。
- クリックから何ミリ秒以内なら成功するか、時間の境界は測定していない。
- 拡張機能の番号は8まであるが、**3台以上の実機動作は未確認**。

## 後日談：受信機1台で動いた。でも、話はそれだけではない

ここまで説明した**2台同時接続の拡張機能は完成し、実機でも動きました**。その後、子供たちとScratch作品を作っている途中で「受信側のmicro:bitは、1台でいいんじゃない？」と言われました。

確かに、送信側2台のmicro:bitで**同じ無線グループ**を使えば、受信機を1台にできます。USBシリアル1本で受信できるところまで実機で確認しました。**作品全体のScratchプログラムは、まだ制作中です。**

自分でも、ずいぶん頭が固かったと思います。送信機ごとに受信機を置くという構成に、いつの間にか縛られていました。

ただし、受信機を1台に集約すると、送信元を区別するためのデータ形式や名前を決め、それに対応する中継処理とScratch側の振り分け処理が必要になります。子供たちが**各自のmicro:bitとScratchのプログラムを独立して作り、後から統合する**という点では、マルチシリアル構成の方が扱いやすい面があります。

受信機を減らす構成は、micro:bitを1台分節約できるので、費用面では大きなメリットがあります。一方で、プログラムの独立性と共同開発のしやすさにはコストが生じます。

**ハードウェアを減らす工夫と、ソフトウェアを分離する工夫は別の話。** 今回作ったマルチシリアル拡張は、独立した通信経路を必要とする場面で引き続き使えます。**この利点はmicro:bitに限らず、複数のシリアル機器をScratchから使う場合にも共通します。**

## おわりに

APIのドキュメントを読んで設計しても、実機で試すと、想定したエラーだけが返ってくるとは限りませんでした。

今回、特に重要だったのは、例外処理を増やし続けるのではなく、**不確かな動作に依存しない接続手順へ設計を変えたこと**です。画面のクリックを1回追加するだけで、利用者にも説明しやすい動作になりました。
